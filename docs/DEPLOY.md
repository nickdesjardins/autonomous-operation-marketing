# Putting the showcase online, step by step

**Status (15 October 2026): online.** Steps 1 to 5 and 7 were followed to put it there; step 6
(the scheduled test's key) is still to do. They stay here as the way to check it, change it, or
rebuild it from scratch. The section
[How far this guide has been tried](#how-far-this-guide-has-been-tried) says what was verified
and what was not.

| What | Where | Address |
|---|---|---|
| The **project page**: recorded runs, the walkthrough, wakes the demo | GitHub Pages | <https://nickdesjardins.github.io/autonomous-operation-marketing/> |
| The **live demo**: the API with its playground at `/` | Render (free web service, Python runtime) | <https://multi-agent-ops-pipeline.onrender.com/> |
| The **database**: PostgreSQL, inventory and checkpoints | Neon (free plan) | not public |
| The **language models** | OpenRouter free models | not public |

The project page is the address to give to people. The live demo sleeps after 15 minutes
without a visit and needs about a minute to wake; the project page starts waking it as soon as
it opens.

In this guide, **the service name** is the part of the demo's address between `https://` and
`.onrender.com`. `render.yaml` asks for `multi-agent-ops-pipeline`; if Render adds letters to
it, use the name it gave wherever this guide shows that one.

## Where each secret goes

| Secret | This GitHub repository | Render | Your computer |
|---|---|---|---|
| OpenRouter key (starts with `sk-or-v1-`) | **only** as the Actions secret `OPENROUTER_API_KEY`, read by the model-check job alone (step 6) | `OPENROUTER_API_KEY`, typed once in step 4 | `.env.local` |
| Neon connection string (`DATABASE_URL_UNPOOLED`, starts with `postgresql://`) | **never** | `DATABASE_URL`, typed once in step 4 | `.env.local` |
| Webhook signing key (`WEBHOOK_SECRET`) | **never** | generated by Render (`generateValue: true` in `render.yaml`), nothing to type | only if you run the showcase locally |
| Inbound key (`API_KEY`) | **never** | not needed: in demo mode the routes are open and the budget protects them | not needed |

The two workflows that run on every push (`tests.yml`, `pages.yml`) use no secret at all. Never
paste a key into `render.yaml`, a commit, a chat or a terminal command. The app also refuses a
key that looks like a connection string at start-up (and never echoes the value), so pasting the
database line into the key box cannot send the database password to OpenRouter.

## Step 1: put the code on GitHub (10 minutes): done on 15 October 2026

The folder is not a git repository yet. Create an empty **public** repository named
`autonomous-operation-marketing` on <https://github.com/new> (no README, no licence, no
`.gitignore`: the folder has them). Then, in PowerShell, in the project folder:

```powershell
git init
```

```powershell
git add -A
```

Git may print lines saying that LF will be replaced by CRLF in some files. They are warnings
only. Now check that no private file is about to be published. The only line printed must be
`.env.example`:

```powershell
git ls-files | Select-String -Pattern "env|pdf|Career"
```

`.gitignore` keeps `.env`, `.env.local`, `model_cache.json` and the career guide PDF out. If
`.env`, `.env.local` or anything ending in `.pdf` appears, stop and fix `.gitignore` before
committing. Otherwise:

```powershell
git commit -m "Autonomous multi-agent operations and marketing pipeline"
```

```powershell
git branch -M main
```

```powershell
git remote add origin git@github.com:nickdesjardins/autonomous-operation-marketing.git
```

```powershell
git push -u origin main
```

For later changes: `git add -A`, the same `git ls-files` check, `git commit -m "..."`,
`git push`. If `git commit` says `nothing to commit, working tree clean`, or `git push` says
`Everything up-to-date`, nothing went wrong: there was nothing new to publish.

One more thing to know before the first push: `DEFAULT_PUBLISHED_URL` in `app/config.py` names
this repository (`nickdesjardins/autonomous-operation-marketing`) as the place where the tested
model chain is published. If the repository gets another name, change that constant at once.

## Step 3: create the database on Neon (5 minutes): done on 15 October 2026

1. Go to <https://console.neon.tech> and sign in (the account from Project 2 is fine; a free
   plan may hold several projects, within its limits).
2. **New project.** Name it `autonomous-operation-marketing`, PostgreSQL 16 or newer, region
   **US East (N. Virginia), us-east-1**: `render.yaml` puts the service in Virginia, and the
   region of neither can be changed later.
3. On the project's page, click **Connect** (or **Connection details**). Pick the database
   and role Neon created, and **switch connection pooling off**: you want the **direct**
   connection string. Its host name must not contain `-pooler`. (The app works through the
   pooler too, because it opens connections with `prepare_threshold=0`, but it runs its own
   small pool and the direct string is the one `render.yaml` asks for.)
4. Copy the connection string. It starts with `postgresql://` and ends with
   `?sslmode=require` (sometimes followed by `&channel_binding=require`). Paste it into
   `.env.local` on your computer as `DATABASE_URL_UNPOOLED=` and keep it there: step 4 copies
   it from that file, and step 7 uses it to record the runs.

Nothing needs to be created in the database by hand. At start-up the service runs the DDL for
`inventory_skus`, `webhook_audit_log` and `webhook_inbox`, upserts the four sample SKUs and
runs the checkpointer's own `setup()`, which creates the LangGraph checkpoint tables.

## Step 4: create the live demo on Render (15 minutes): done on 15 October 2026

Before you start, open `.env.local` in an editor. You will copy two values from it. Copy only
the part after the `=` sign, without quotes.

1. Go to <https://dashboard.render.com> and sign in.
2. Click **New > Blueprint**.
3. Find `autonomous-operation-marketing` in the list and click **Connect**. If it is not in the
   list, Render's GitHub app is not allowed to see it yet: follow Render's link to configure
   GitHub access (or open <https://github.com/settings/installations>, **Render > Configure**),
   add the repository under repository access, save, and come back.
4. **Blueprint name**: anything, for example `autonomous-operation-marketing`. **Branch**:
   `main`. Leave **Blueprint path** empty.
5. Render lists what it will create: **one web service, `multi-agent-ops-pipeline`, plan
   Free**, Python runtime. Check that it says Free. Do not add a card unless Render asks:
   without one, Render pauses a free service when a limit runs out instead of billing.
6. Fill in the two boxes Render shows. It asks for them **only this once**:
   * `OPENROUTER_API_KEY`: the value of `OPENROUTER_API_KEY` from `.env.local`. It starts with
     `sk-or-v1-`. If what you copied starts with `postgresql://`, it is the wrong line (the
     service would refuse to start: "the API key does not look like a key").
   * `DATABASE_URL`: the value of **`DATABASE_URL_UNPOOLED`** from `.env.local`, the direct
     Neon string from step 3. Quotes or a `psql ` prefix copied along are stripped by the app,
     but a string that does not start with `postgresql://` or `postgres://` is refused.
7. Click **Deploy Blueprint**. Render creates the service and generates `WEBHOOK_SECRET` by
   itself. Open the service, then **Deploys**, and click the deploy at the top to follow its
   log. The build is `pip install -r requirements.txt` (a few minutes; nothing else is
   downloaded). Then the start command runs `uvicorn app.main:app --workers 1`, and the log
   should show, in this order:
   * `Inventory schema ready (4 sample SKUs)`: the tables exist and the seed is upserted;
   * `Demo mode: 2 runs/visitor/min, 12/visitor/day, 6/min, 120/day, 2 in flight, max_revisions
     capped at 2, webhook target self`;
   * `Startup complete: multi-agent-ops-pipeline v1.0.0`;
   * `Model choice: automatic. Using the tested default [...]` (because `OPENROUTER_MODELS` is
     blank), then `Nothing is tested until a request fails. ...`;
   * until step 6 has published a chain: `The published list at https://raw.githubusercontent.com/...
     was not used: nothing is published at that address (HTTP 404). The chain stays [...]`,
     which is information, not an error; afterwards a line saying which published chain is in
     use, and one line per model of the chain with the catalogue's word on it.
   A few `Database not ready (...), attempt 1 of 4; retrying in 2 s` lines before that are
   normal while Neon resumes. Wait until the deploy shows **Live**. If it shows **Failed**, the
   end of the log names the failing line; see [Troubleshooting](#troubleshooting).
8. The service's address is at the top of the service page.
9. Check it. Each of these opens in a browser (replace the service name if Render changed it):
   * `https://multi-agent-ops-pipeline.onrender.com/livez` shows `"status":"alive"`;
   * `https://multi-agent-ops-pipeline.onrender.com/health` shows `"status":"ok"`,
     `"connected":true`, `"checkpointer_ready":true`, `"inventory_skus":4`, `"mode":"automatic"`
     and `"target":"self"` with `"configured":true`;
   * `https://multi-agent-ops-pipeline.onrender.com/` opens the playground. Pick a SKU and a

    ```powershell

    ```

    `NR-VITD-1000` is the out-of-stock SKU, so the run ends at the inventory node and no model
    is called, but the budget still counts it. Lines 1 and 2 say `out_of_stock`; line 3 says
    "Too many runs from this address; please wait a minute." Then open the playground on a
    phone on mobile data, within the same minute, and start a run: it must be accepted. If the
    phone gets the same refusal, every visitor shares one budget (the demo is still safe; see

If you typed a value wrong in step 6: service page > **Environment** > edit the value >

## Step 6: give the scheduled model test its key (3 minutes)

`.github/workflows/model-check.yml` ("Model check") runs `python -m app.models.published` every
day at 06:17 UTC and tests the free models when a test is due (about once a week, or when
OpenRouter's list changed): the three cases of `app/models/cases.py` per candidate, 12 free
requests at the very most. It publishes the chain it confirmed to `chain.json` on the branch
`tested-models`, and every service in automatic mode reads that file at start-up
(`DEFAULT_PUBLISHED_URL` in `app/config.py`). The job runs with `CHECKPOINTER=memory` and
`MODEL_PUBLISHED_URL=null`, so it opens no database and reads no list of its own. It needs one
repository secret, and nothing else in the repository does.

1. On GitHub, open the repository, then **Settings**, then under **Security** click
   **Secrets and variables**, then **Actions**.
2. Click **New repository secret**. **Name:** `OPENROUTER_API_KEY` (exactly this). **Secret:**
   an OpenRouter key. A key made only for this job (on <https://openrouter.ai/keys>, with a
   credit limit of 1 dollar and auto top-up off) can be withdrawn without touching the key the
   service uses.
3. Open the **Actions** tab, click **Model check** in the left list, **Run workflow**, branch
   `main`, **Run workflow**. Leave the box unticked: no chain is published yet, so a test is
   due anyway. It spends three free requests per candidate model, 12 at most.
4. When it is green, the branch menu of the repository (top left, where it says **main**) lists
   **tested-models**, holding `README.md` and `chain.json`. Only one step of the first job ever
   sees the key, and the job that writes to the repository runs no downloaded code. The run's
   summary lists each model's verdict and the published chain.

Without the secret the job still says what is due, in a yellow warning on the run, tests
nothing and publishes nothing; services then start from `DEFAULT_MODEL_CHAIN`. A red run means
the owner has something to do: open the job "Test the free models, if a test is due" and read
the end of its step "Decide, test, and write the file to publish" for a line that begins
"Failing this run on purpose:".

## Step 7: record the runs for the project page (10 minutes): done on 15 October 2026

The page shows `site/recorded/runs.json`, which `scripts/record_runs.py` writes by driving the
real application in-process, through the same routes, graph, PostgreSQL checkpointer and model
chain as the deployed service; nothing in it is edited by hand. Until that file exists the page
says so in one sentence and shows nothing else under "Recorded runs". The script needs
`CHECKPOINTER=postgres` with a reachable database and the OpenRouter key, both read from
`.env` / `.env.local`; demo mode is switched off for the recording, so the runs do not count
against the public budget. It records six scenarios (`happy-path`, `self-correction`,
`escalation`, `edit`, `reject`, `out-of-stock`); each spends 2 to 4 free requests (a draft and
an audit per attempt, at most one redraft), the out-of-stock one none.

1. Either record against Neon (the script reads `DATABASE_URL_UNPOOLED` from `.env.local`, the
   string from step 3), or start an embedded PostgreSQL on your computer and keep it running
   for the recording:

   ```powershell
   .\.venv\Scripts\python.exe scripts\run_live_db_tests.py --serve
   ```

   The first run installs `pgserver` into the virtualenv (its data lives in the git-ignored
   `.pgdata/`). It prints a local connection string (user `postgres`, no password: nothing
   secret) and keeps the server up until Ctrl+C. In a second PowerShell, point the recording at
   it for that session. If `.env.local` holds `DATABASE_URL_UNPOOLED` from step 3, that value
   wins over `DATABASE_URL` (`app/config.py`), so override that one:

   ```powershell
   $env:DATABASE_URL_UNPOOLED = "<the printed URL>"
   ```

2. Record the runs (all six, or `--only reject,edit` for a subset):

   ```powershell
   .\.venv\Scripts\python.exe scripts\record_runs.py
   ```

3. Check the recordings, then commit `site/recorded/runs.json` and push, as in step 1. The
   **Project page** workflow runs `tests/test_site.py`, which validates every recorded run
   against the schemas, the prompts and the code and looks for secrets in it, and publishes.

   ```powershell
   .\.venv\Scripts\python.exe -m pytest tests/test_site.py -q
   ```

## Good to know about the free plans

* **Sleeping.** The demo sleeps after 15 minutes without a visit and takes about a minute to
  wake. The project page wakes it automatically. Render's health check is on `/livez`, which
  never touches the database, so Neon's compute can suspend between visits; `/health` does
  reach it and wakes it.
* **Neon's compute suspends when idle** and its connections drop. The app expects that: the
  pool checks a connection before handing it out, keeps idle ones for four minutes at most, and
  retries the start-up schema check `DB_STARTUP_RETRIES` times while the compute resumes. The
  free plan has a monthly compute allowance; a demo that is visited a few times a day stays far
  inside it.
* **Builds cost minutes.** Render gives a monthly budget of build minutes; this service's build
  is one `pip install`, a few minutes. A push that changes only `site/`, `docs/`, `README.md`,
  `.github/`, `tests/`, `scripts/` or `benchmarks/` does not rebuild the service
  (`ignoredPaths` in `render.yaml`).
* **Change settings in `render.yaml`, not in the dashboard.** For every setting the file lists
  with a value, edit the file and push: a later Blueprint sync can put the file's value back over
  a dashboard edit. The dashboard is the place only for `OPENROUTER_API_KEY`, `DATABASE_URL`,
  the generated `WEBHOOK_SECRET`, and settings the file does not list (`OPENROUTER_MODELS`, for
  one).
* **Fixed once created.** The region (Virginia, next to the Neon database in us-east-1) and the
  `onrender.com` address cannot be changed later.
* **Hours.** A workspace gets 750 free instance hours a month, shared by all its free services
  (Projects 1 and 2 included). Sleeping services use none. A service kept awake around the
  clock uses up to 744, and when the hours run out Render suspends every free service until the
  1st.
* **OpenRouter's free allowance** is per account and per UTC day (50 requests without credits,
  1000 after a one-time 10 dollar purchase), shared by every project, local run, smoke test and
  the scheduled job that uses the same account. The demo stops admitting runs when fewer than
  `OPENROUTER_ALLOWANCE_RESERVE` (100, or a fifth of the allowance when that is smaller) are
  left.

## What protects the public demo

| Risk | Protection |
|---|---|
| Someone spends the day's free requests | Per visitor: 2 runs a minute and 12 a day. Everyone together: 6 a minute and 120 a day. Each run is admitted for `2 * (max_revisions + 1)` calls, and `max_revisions` is capped at 2. And the service asks OpenRouter for the real count once a minute and stops at a reserve of 100 (or a fifth of the allowance). |
| Someone pretends to be many visitors | The address comes from `CF-Connecting-IP`, which Cloudflare (in front of every Render web service) overwrites; the left-most `X-Forwarded-For` entry, which a client can write, is never used. IPv6 visitors are grouped by their /64 network. |
| Someone floods the small instance | At most 2 runs execute at once (more get `503` with `Retry-After: 5`), briefs are capped at 300 characters, every request body at 32 KB, and request starts to OpenRouter are paced at 20 a minute. |
| A typo makes the service call a paid model | `OPENROUTER_FREE_ONLY=true` refuses any model id that does not end in `:free`, at start-up and again at call time; the chain the service chooses for itself accepts only `vendor/model:free` ids, and so does a test of the models. |
| Someone keeps pressing "Test the free models now" | A press is admitted like a run through the demo budget, for the 12 requests a test sends at most (so the per-visitor and global limits and the allowance reserve apply), the button may start 4 tests a day for everyone together, tests are kept 15 minutes apart whoever starts them, one runs at a time, and the button is refused when the day's allowance is low or cannot be read. In production the route also wants the page's `Accept: application/json`, which keeps a plain form or a link from starting one; it is not a protection on its own. |
| The OpenRouter key leaks | Give the key a credit limit of 1 dollar and keep auto top-up off: free models cost nothing, so the limit never stops the demo, and it caps what a leaked key could spend. Replace it as in Day-to-day. |
| The database string is pasted into the key box | Start-up refuses a key that contains `://` or whitespace, without echoing it, so the database password is never sent to OpenRouter. |
| The webhook reaches somebody else's server | In demo mode `WEBHOOK_TARGET=url` is refused at start-up. The only targets are the service's own receiver and a dry run. |
| Someone forges a delivery into the inbox | The receiver recomputes the HMAC-SHA256 signature over `timestamp.delivery_id.body` with `WEBHOOK_SECRET`, compares it in constant time, refuses a timestamp more than 300 seconds off, and keeps a repeated delivery id once. The delivery id is signed, so a captured delivery cannot be replayed under a fresh id, and the thread's state holds only a fingerprint of the signature, not the header the receiver verified. |
| A brief tells the model what to do | The brief is wrapped in tags with a random suffix per request and declared untrusted; the audit prompt treats instructions inside the copy as part of the copy. The deterministic checks run whatever the model says. |
| Nothing leaves without a person | The graph stops before the webhook node; only an `approve` or `edit` resumes it; a `reject` is written as if the node had run, so it never does; and the node itself refuses to send unless the recorded review status is `approved` or `edited`. |
| An error message leaks a key, a quota or SQL | Clients get the provider's name, "temporary" or "permanent", and an incident id; a database failure is a `503` with an incident id; validation errors never echo the rejected input; a bad setting is reported without its value. |
| The inventory contains something private | The four SKUs, their claims, warnings and licence numbers are written for the demo (`app/seed.py`). |

Free endpoints may keep and train on what they are sent. Keep the sample SKUs; do not load a
real product dossier while the service runs on free models.

## Day-to-day

**Run the showcase on your own machine.** This starts it in demo mode without Docker, with the
OpenRouter key and the database from `.env.local` (`DATABASE_URL` to the Docker container,
`DATABASE_URL_UNPOOLED` to Neon, or `CHECKPOINTER=memory` for no database at all). For this
process only it sets `DEMO_MODE=true`, `WEBHOOK_TARGET=self` and `PUBLIC_BASE_URL`, and it
generates a `WEBHOOK_SECRET` when none is set:

```powershell
.\.venv\Scripts\python.exe scripts\run_local_demo.py
```

Open <http://127.0.0.1:8011/> in a browser (`--port` changes it); press Ctrl+C in PowerShell to
stop it. Each run counts against the same free allowance as the live demo. `render.yaml` is not
read, so `/docs` stays visible unless `.env.local` sets `ENVIRONMENT=production`.

**Check the local key and model chain** (two free requests; reads `.env.local`, not Render):

```powershell
.\.venv\Scripts\python.exe scripts\openrouter_smoke.py
```

**Replace the OpenRouter key.** Create the new key on <https://openrouter.ai/keys> (credit
limit 1 dollar, auto top-up off on <https://openrouter.ai/settings/credits>), put it in
`.env.local`, run the smoke script, then on Render: service > **Environment** >
`OPENROUTER_API_KEY` > edit > paste > **Save and deploy** (not **Save only**). Wait for
**Live**, start one run on the demo, update the GitHub secret from step 6, and only then delete
the old key.

**Read the webhook secret.** Service > **Environment** > `WEBHOOK_SECRET`. You only need it to
verify deliveries from outside the service, which the demo never sends.

**See what arrived.** `https://<service name>.onrender.com/api/v1/webhooks/inbox?limit=20`
lists the last deliveries the receiver accepted, newest first.

**Change the limits.** Edit the `RUN_*`, `DEMO_MAX_REVISIONS` and `OPENROUTER_ALLOWANCE_RESERVE`
values in `render.yaml` and push; the service rebuilds and restarts.

**Change the sample SKUs.** Edit `app/seed.py`, then regenerate the SQL file and commit both:

```powershell
.\.venv\Scripts\python.exe -m app.seed
```

The start-up upsert writes the new values to Neon on the next deploy (`ON CONFLICT DO UPDATE`).
Then record the runs again (step 7).

**Pin the chain, or go back to automatic.** To run exactly two models, set `OPENROUTER_MODELS`
in the service's **Environment** (comma-separated ids that end in `:free`) and **Save and
deploy**; delete the variable to hand the chain back to the service. On your computer, delete
`model_cache.json` and restart to go back to the tested default.

**Keep the demo awake (optional, part of the day only).** A free cron-job.org job can request
`/livez` every 10 minutes so visitors do not wait for a cold start. `/livez` never touches the
database, so Neon still suspends. Do not do this around the clock: one service awake all day
uses up to 744 of the workspace's 750 free hours, which the other projects share.

## Troubleshooting

| What you see | What it means | What to do |
|---|---|---|
| The repository is missing under **New > Blueprint** | Render's GitHub app cannot see it | GitHub > **Settings > Applications > Render > Configure** > add the repository. |
| The deploy fails with "the API key does not look like a key (was another line pasted along with it?)" | Another line, or a connection string, was pasted into the key box | Service > **Environment** > `OPENROUTER_API_KEY`: paste the `sk-or-v1-...` value, **Save and deploy**. |
| The deploy fails with "DATABASE_URL must be a PostgreSQL connection string starting with postgresql:// (paste the string itself, without quotes)" | The value is not a connection string, or was copied incompletely | Service > **Environment** > `DATABASE_URL`: paste the `DATABASE_URL_UNPOOLED` value from `.env.local`, **Save and deploy**. |
| The log shows "Database not ready (...), attempt 3 of 4; retrying in 6 s", then a traceback, and the deploy fails | The database cannot be reached: a wrong host or password in the string, or the Neon project is not active | Check the string against the Neon console, and that the project is not paused. The exception type is in the line; the URL never is. |
| The deploy fails with "WEBHOOK_SECRET is required to sign deliveries (any long random string)" | `WEBHOOK_SECRET` is empty, which can happen if the service was created outside the Blueprint | Service > **Environment** > add `WEBHOOK_SECRET` with any long random string, **Save and deploy**. |
| The deploy fails with "DEMO_MODE never dispatches to an external URL: set WEBHOOK_TARGET to self or dry_run" | `WEBHOOK_TARGET=url` was set on a demo | Set it back to `self` (in `render.yaml`, then push). |
| The deploy fails with "OPENROUTER_MODELS contains non-free models [...]" | An id without `:free` was put in `OPENROUTER_MODELS` | Fix the id, or remove the variable to go back to automatic. |
| The log says "No API key for LLM_PROVIDER=openrouter; runs will answer 503 until it is configured" and runs answer `503` "LLM provider 'openrouter' is not configured (missing API key)" | The key variable is missing or empty | Service > **Environment**: set `OPENROUTER_API_KEY`, **Save and deploy**. `/health` shows `"configured": false` meanwhile. |
| `/health` says `"status": "degraded"` with `webhook.configured: false` and `url_host: null` | The `self` target has no address: `RENDER_EXTERNAL_URL` is not set (another host), or locally `PUBLIC_BASE_URL` is empty | Set `PUBLIC_BASE_URL` to the service's public address. Until then an approval ends `dispatch_failed` with "no target address configured". |
| `/health` answers `503`, or requests answer `503` "The database is unavailable; retry later. Incident ..." | The database cannot be reached. Right after a long idle period Neon may still be resuming. | Retry after a few seconds. If it persists, check `DATABASE_URL` and the Neon console. The log line carries the incident id from the message. |
| Runs answer `503` "The demo is running other pipelines; please try again in a few seconds." | Two runs were already executing (`RUN_MAX_INFLIGHT`) | Nothing to fix; the `Retry-After` header says when. |
| Runs answer `429` | A budget rule was reached; the message says which one and the header when it resets | "Too many runs from this address", "This address has reached its runs for today", "The demo is busy right now" and "The demo's daily run limit is reached" come from the `RUN_*` values in `render.yaml`. "Today's free-model allowance is used up; the demo resumes tomorrow (UTC)" is different: the OpenRouter account is down to its reserve, counting every project, local run and the scheduled job on that account. Wait until midnight UTC. |
| Runs answer `502` "Upstream provider error (openrouter-auth): permanent failure; incident ..." | OpenRouter refused the key: mistyped, saved with **Save only**, or deleted before the new deploy was **Live**. `/health` still says `"configured": true`, because it only checks that a key is set. | Run `scripts\openrouter_smoke.py` locally with the key from `.env.local`; if it works, paste that value into service > **Environment** > `OPENROUTER_API_KEY`, **Save and deploy**, wait for **Live**. |
| Runs answer `502` or `503` "Upstream provider error (openrouter): ..." | Every model of the chain failed on that request (the log line names each model and its reason: "rate limited (429)", "model not found (404); withdrawn?", "upstream provider error", "invalid output") | `503` is temporary: retry in a minute. `502` on every run means the chain is gone: with `OPENROUTER_MODELS` blank the service repairs it after the failed request; otherwise pick ids that end in `:free` on openrouter.ai/models and set them in the service's **Environment**. |
| A review answers `409` "This thread is not waiting for review (status '...')" | The thread already ended, was already reviewed, or never reached the gate (`out_of_stock`, `sku_not_found`, `invalid_request`) | Read the thread with `GET /api/v1/workflows/{thread_id}`; only `awaiting_human_review` with `next_nodes: ["webhook_dispatch"]` can be reviewed. |
| A review answers `404` "Unknown thread" | The id is not a UUID, or no checkpoint exists for it (a thread from before a database change, or from a `CHECKPOINTER=memory` run that restarted) | Start a new run. |
| A run ends `dispatch_refused` with "webhook refused: the human review status is 'pending'" | The graph was resumed without a recorded decision (for example `ainvoke(None)` from a shell) | Use the review endpoint; the node will not send without `approved` or `edited`. |
| The receiver answers `503` "WEBHOOK_SECRET is not configured" or `401` "Invalid or missing webhook signature" | The service has no secret, or the sender signed with another one or a stale timestamp (over 300 seconds) | Check `WEBHOOK_SECRET` on both sides and the sender's clock. |
| A request answers `413` "Request body exceeds MAX_JSON_BODY_BYTES (32768 bytes)" | The body is larger than 32 KB (an `override_copy` well past the schema's limits) | Shorten it; the schema's field limits add up to under 16 KB of copy. |
| A request answers `422` | The body failed validation; the response names the field and the rule, never the value | Typical: `sku_code` not 3 to 32 upper-case letters, digits or hyphens; `campaign_angle` under 3 or over 300 characters; `edit` without `override_copy`; `marketplace_bullets` not exactly five. |
| Your phone on mobile data is refused after your computer hit its limit (step 4.10) | Render did not pass `CF-Connecting-IP`, so all visitors share one budget | The demo stays safe (that is the stricter failure). Ask Render support which header carries the client address, and set it as `CLIENT_IP_HEADER` in `render.yaml`. |
| The log says "Could not save the chosen model chain in ... The service goes on using it from memory" | The disk is read-only or forgotten (normal on Render) | Nothing to fix: the chain is kept in memory, and a restart starts from the published chain or the tested default. |
| The log says "The published list at ... was not used: nothing is published at that address (HTTP 404)" | The scheduled job has not published a chain yet (step 6), or it has no key | Do step 6. Until then the service uses `DEFAULT_MODEL_CHAIN`, which is fine. |
| The log says "The published list ... was not used: it was made by another version of the test" | The published `chain.json` was made before a change to the prompts, the cases, the rules or the default chain (its fingerprint differs) | Nothing to do: the push that changed them started **Model check**, whose next publication fits this version. Check that the run is green. |
| The log ends with "Test ... found no free model that passes, and ..." and every run answers `502` or `503` | OpenRouter no longer offers any model of the chain (or this account cannot call them) and no other free model passed the three cases | The service tests again after the next failed request, 15 minutes after the last test at the earliest. To choose yourself: pick ids that end in `:free` on openrouter.ai/models, set `OPENROUTER_MODELS` in the service's **Environment**, **Save and deploy**. |
| **Model check** shows a yellow warning that the job has no key | The secret of step 6 is missing or has another name | Add it, then start the workflow by hand. |
| **Model check** is red | The owner has something to do: open the run, the job "Test the free models, if a test is due", and read the end of its last step for a line that begins "Failing this run on purpose:" | Follow that line. A red run without it means the job itself broke (a traceback at the end of the step). |
| The project page still says the demo is not online, or has not answered | The link in `site/index.html` is not yet updated (step 5), is mistyped (the **Tests** run is then red), or the service is failing to start | Open `/livez` on the service. If it answers, fix the link and push. If it does not, read **Deploys** and **Logs** on Render. |
